# Customer access and private profile photos

Registration asks for Student / Regular and the lead source. Others requires details. Category is separate from membership standing. Public registration retains the existing pending-visitor/attendance behavior; admin approval preserves the internal ID, visits, category, source and photo path. Existing profiles stay unclassified until an admin edits their category; existing lead source is not invented.

The public entry offers Create Account or Check In, followed by the existing phone lookup. A matching profile is reused. Registration includes the first visit and still requires profile verification. On the confirmation screen the optional photo step can be skipped or retried independently; a photo failure never cancels registration/attendance.

Customer access at /customer uses the requested phone-only model without OTP. It is intentionally limited, and does not prove phone ownership. A random 256-bit opaque token is stored only in an HttpOnly, SameSite=Strict cookie; only its SHA-256 hash is stored on the server. Sessions expire after 30 minutes. Customer endpoints bind to that record, never accept an arbitrary customer ID as authority, recheck deletion, reject cross-origin writes and throttle access. Only membership/category and the customer's limited payment status are exposed; profile contact data, weights, RFID fields, audit and other customers remain inaccessible.

Photos accept JPG, PNG and WebP up to 5 MB and 16 million decoded pixels. The server decodes, strips metadata, rotates/resizes and reencodes WebP before storage. The private profile-photos bucket has no public access. Authorized endpoints stream images with no-store, nosniff and a restrictive content policy; no signed/public object URLs are returned. Firebase authorizes all access because the privileged Supabase server client bypasses RLS.

Setup executed: node scripts/private-images-setup.mjs created/verified the private bucket without public policies or test objects. Repeat for another environment after configuring server-only Supabase credentials.

Each upload has a durable profileImageUploads recovery record and stable operation ID. Upload/link retries cannot replace a different payload or resurrect a deleted profile. An uncertain link response never triggers destructive cleanup of a potentially linked image. Under the October 28 owner-approved policy, abandoned uploads keep a 24-hour recovery window; replaced photos become eligible immediately and deleted-profile photos are queued for the next cleanup. POST /api/images/cleanup with administrator or private maintenance authorization examines at most 100 eligible jobs, rechecks both profile namespaces and deletes only unreferenced images; current profile photos remain while the profile exists. Deletion revokes access immediately. Physical removal retries external failures. Payment review's Run retention cleanup button runs the protected maintenance locally. Hosting/unattended scheduling remain deferred. See audit-and-retention.md.

Production app and Firebase rules rollout, physical hardware checks, and visual review on the actual deployed/mobile environment remain handover checks. All non-SMS work operates without SMS configuration.
