## Implemented behavior

- JPG/PNG/WebP images up to 5 MB are decoded, stripped of metadata and stored privately as WebP. PDF/password-protected/non-image attachments are rejected; an unreadable screenshot remains evidence for manual review.
- GCash only appears when the readiness gate passes. Receipt upload precedes attendance, with a stable operation ID, immutable object path and unique request link. The authoritative attendance transaction validates a server-held receipt proof bound to the customer, charge, amount and expiry. Missing, fake, cross-customer or expired evidence cannot become a completed payment submission.
- A durable Firestore intent coordinates Supabase metadata/object upload with Firestore linking. Repeated uploads recover the same object; a different payload cannot reuse the operation. An ambiguous attendance response never removes a potentially linked receipt. Link/correction outboxes are reconciled by the worker; expired unlinked objects are cleaned in bounded batches after a 24-hour recovery window.
- Every new charge receives a unique `TB-` number from a transactionally allocated 12-digit sequence, independent of record counts. This is the initial display convention; the owner can review the display format later without changing financial IDs. Existing blank numbers require an explicit metadata-only migration if such records were created before this phase; no live financial records were created by this run.
- Opening a pending receipt review starts Tesseract for that receipt only, using bundled English language data and a 45-second extraction timeout. Completed results are reused on later openings; Scan again explicitly rescans. Failed attempts can be retried on the next opening or manually. New uploads wait in needs_review without entering a background OCR queue. A conditional update and short claim token prevent concurrent scans of the same receipt; cleanup can revoke that token before removing evidence. Legacy queued records are handled on opening as well. No OCR result approves or rejects a payment, and scans preserve confirmed values and the authoritative review revision.
- OCR extracts labelled reference and amount conservatively. Low confidence, ambiguity, unreadable images and mismatches require review. Normalize only numeric formatting and keep leading zeros; never guess OCR character replacements. Reference reuse flags are advisory until the unique Firestore claim is made in the authoritative approval transaction.
- The admin receipt panel displays the private image/extraction, flags amount/reference conflicts, and saves confirmed reference/amount with a reason and revision check. Its durable correction outbox protects review data when Supabase is unavailable. Saving a receipt review is separate from payment approval.
- Metadata has unique request/object links, lookup/queue/cleanup indexes, forced RLS and no anon/authenticated privileges or policies. The privileged server client must separately authorize every request with Firebase. Customer image access is bound to the session; raw extraction/review access is admin-only.
- Deleted customer IDs have minimal tombstones so an old registration event cannot attach a new identity to retained financial history. Image/text access is revoked when the profile freezes/deletes. Receipt evidence still follows the October 28 approved retention policy after profile deletion: rejected evidence 180 days from final rejection, approved evidence protected until confirmed filing-based accounting expiry, pending reviews and dispute/legal holds protected. The worker removes eligible objects/raw OCR while preserving minimal financial identifiers/amounts/reference history. Unlinked uploads use the existing 24-hour recovery cleanup. See audit-and-retention.md for controls, recovery and accounting-date requirements.

## Operations

Opening a pending receipt review posts `{ action: "extract", receiptId }` to `/api/receipts/review`, which returns after scanning that specific receipt. Scan again adds `force: true`. Two open reviews share the receipt's in-progress result; the second view waits by reading status, without dispatching other receipts. The admin can still enter unclear values manually and must save a reviewed reference/amount before approval.

`/api/receipts/worker` now performs only link/correction recovery and retention/orphan cleanup. Schedule it with the existing server-only CRON_SECRET if regular cleanup is desired; it never invokes OCR. Existing queue SQL remains for migration compatibility but is not called by the application. No database migration is required for on-demand scanning. Configure hosting support for Node workers, sharp, bundled language data and the review route's 120-second budget; its output tracing includes the Tesseract runtime and language files.

Initial local verification included real Tesseract on synthetic evidence, local PostgreSQL-compatible migration/RLS/uniqueness/lease checks, and in-memory cross-system failure/concurrency tests. October 28 live-backend verification is recorded separately above; neither test set claims a real GCash transfer or a deployed production OCR runtime.
