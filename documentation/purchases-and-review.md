# Purchases, renewals and administrator decisions

**Owner-approved display/policy — October 28, 2026:** keep TB- plus 12-digit transaction numbers separate from GCash references. Keep expected daily charges plus approved membership purchases, pending requests awaiting review with renewals separately displayed, and confirmed collections attributed to confirmation date. Admin profile verification and payment approval remain separate; payment approval activates applicable membership. All five choices were explicitly accepted without requesting code changes.

- Customers enter their saved phone number at /customer. Only a verified official profile can submit membership purchases; profile approval remains a separate administrator step. Customer requests use the server session's ID and cannot target another person. The page shows configured single-month pricing, coverage preview, Cash / GCash (when private receipt setup is ready), outcomes and rejection reasons, and linked replacement submissions.
- Monthly prices stay unset until an administrator configures them. Package/custom-expiry amounts are not inferred or enabled. Active coverage extends from the existing future expiry; expired coverage restarts on the eventual approval date. Calendar month ends are clamped and final expiry uses exclusive Philippine midnight.
- New administrator-entered memberships atomically create an official guest profile plus a priced pending cash request; they do not silently activate membership. Renewal and guest conversion screens submit a pending request against the same existing identity. Payment review completes activation after the administrator confirms receipt of funds.
- The Renewal Requests tab lists customer, category, coverage, amount, method, submission date, Tibay number, available GCash reference/receipt and outcome. Its Daily payments tab keeps daily review separate from membership activation. Lists are bounded and paginated; customer status projections omit private profile/receipt/audit details.
- Approval re-reads payment, charge, person and reviewed receipt values inside one Firestore transaction. It compares the displayed final-coverage token and requires explicit acknowledgment after membership changes. It claims a GCash reference, records confirmation, recognizes a membership sale, applies coverage and writes audit evidence atomically. Pending/rejected requests never extend membership, and repeated approvals return the existing outcome without another extension.
- GCash approval requires an explicitly reviewed reference and an amount matching the charge; OCR alone is insufficient. A claimed reference cannot pay another purchase. Daily approval never changes membership, and daily rejection does not erase attendance or its expected charge.
- Rejection requires a reason. A replacement links to the rejected request and original charge, retaining original rate/category/amount snapshots and earlier outcomes. A per-person pending-membership guard and stable operation receipts prevent duplicate submissions. Receipt upload and correction recovery remain the Phase 5 mechanisms.
- Legacy direct renewal/conversion operations are closed. Existing profile date/status corrections remain possible only with an explicit audited correction reason and do not claim a sale; paid extensions use the purchase workflow. The old immediate conversion undo is not a financial void operation and is unavailable after this extension. A separate void/correction workflow remains outside scope.
- Current-category changes and rate edits never rewrite existing financial snapshots. Guest approval/conversion retains person ID, visits, weights and independent RFID ownership.

Local automated checks cover cash and GCash decisions with synthetic/in-memory records, stale review, competing/repeated approvals, duplicate reference rejection, expired-date attribution, replacement links, admin profile creation, and customer-ID boundaries.
