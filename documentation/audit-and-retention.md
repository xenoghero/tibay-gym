# Audit and deletion retention

The owner approved this policy on October 25, 2026: retain minimal internal financial and audit records when a customer is deleted; omit names, phone numbers, addresses, photos and birth dates from retained records.

- Protected administrator operations atomically append audit events alongside changes. Each event records actor UID, action, subject/internal customer ID, server time, operation identifier, relevant operational values and a reason when required.
- The allowlist keeps membership type/status/coverage, category, attendance counts/times, rate values and changed-field names. Profile contact/demographic contents, weight measurements, tokens, credentials, image paths and receipt extraction text are excluded. Profile changes retain field names rather than the sensitive contents. Do not put personal details into free-text operational reasons.
- Financial records contain internal IDs and purchase/payment details. Ordinary profile deletion retains charges, payment requests, approved reference claims, financial operation receipts, admin operation receipts and the new audit collection. Existing profile data, demographics, attendance, weights and the old status/RFID history follow the existing cleanup.
- Deletion first freezes the customer, releases card ownership and cancels enrollment; bounded cleanup can be retried. The audit records both the initial deletion request and final deletion. No successful final-deletion event is written if cleanup fails.
- A deleted subject remains identifiable in audit by its internal ID; the audit view must work without fetching its deleted profile. Access is admin-only through the protected paginated endpoint. There are no browser write permissions for audited collections.
- Minimal internal financial/audit records retain their existing policy; no new automatic ledger purge is introduced. The owner approved the separate photo/receipt evidence durations below on October 28, 2026.
- Deploy the matching application endpoints before enforcing the revised Firestore rules. Rules deny direct admin browser writes to profiles, demographics, weights and old status history; the server performs those changes and writes the new audit event within its transaction.

Audit filters use Philippine dates and include action, customer ID and record ID. Combined queries use the indexes declared in firestore.indexes.json.

## Photo and receipt evidence policy — approved October 28, 2026

- Keep the current profile photo while its profile exists. Replacements become eligible immediately; profile deletion queues photos for the next cleanup. Failed/unlinked uploads retain the existing 24-hour recovery window. Physical removal requires maintenance to run and retries storage failures.
- Keep rejected/replaced receipt images and raw OCR text for 180 days after the payment request's final rejection. Replacement requests have independent evidence; replacing a rejected request never resets its original rejection clock.
- Pending/unknown payment decisions are protected. Approved evidence is protected by default until the owner/bookkeeper confirms that the five-year accounting period applies and supplies the relevant return deadline and actual filing date. Do not infer these dates from payment time.
- For an on-time filing, calculate five calendar years from the day following the deadline; for a late filing use the actual filing date. Dates use midnight Asia/Manila, with leap dates rolled forward to avoid early removal. This implements the chosen period, not automatic determination of the relevant tax return or any exceptional longer legal requirement. [RA 11976 Section 33](https://lawphil.net/statutes/repacts/ra2024/ra_11976_2024.html).
- Independent dispute and legal/accounting holds pause removal. Admins manage these in **Payment review → Retention and holds**, including rows for deleted customers. The same controls appear in receipt review. Pending status, holds and accounting protection still apply after profile deletion; this supersedes the old blanket deleted-profile receipt purge. Photo/customer image access is still revoked immediately on deletion.
- The protected GET/POST `/api/receipts/retention` uses Firebase admin authentication, revision checks, durable operation IDs and sanitized audit events. New Firestore collections are server-only under the existing default-deny rules. No new SQL migration/index, hosting or scheduled resource is required.
- The worker scans 25 receipt intents per run with a rotating cursor, including old records. A transaction orders holds against removal claims: a hold saved before the claim protects evidence; after removal starts the API refuses hold/date edits. Removal is irreversible. It clears raw text and invalidates the OCR lease before deleting the object, then records completion once. Failures remain resumable; upload retries cannot recreate removed evidence.
- Retained minimal payment/reference/audit records are unchanged. Image/text APIs hide evidence as soon as removal starts. No full receipt contents are copied into audit logs. [NPC purpose-based retention principle](https://privacy.gov.ph/data-privacy-act/).

Use **Payment review → Run retention cleanup** locally to run receipt maintenance (including one OCR job) and photo cleanup. Receipt review's existing OCR processing button also runs receipt maintenance. Hosting and unattended schedules remain deferred; elapsed retention does not itself execute a background job. Larger backlogs may require repeated runs. Confirm the relevant return dates with the bookkeeper before setting approved-receipt expiry; no live accounting dates have been invented or saved by this implementation.
